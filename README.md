## 用 GitHub Pages 發布

1. 打開這個 repo 的 GitHub 頁面，點上方的 **Settings**。
2. 左側選單點 **Pages**。
3. 在 **Build and deployment** 的 **Source** 選「**Deploy from a branch**」。
4. **Branch** 選 `main`，資料夾選 `/ (root)`，按 **Save**。
5. 等 1～2 分鐘，頁面上方會出現網址：`https://ikukou0822.github.io/ayaka-fansite/`。
6. 勾選 **Enforce HTTPS**。

之後每次 push 到 `main`，GitHub Pages 都會在一兩分鐘內自動更新。

> 製作時的環境沒有權限呼叫 GitHub 的 Pages API 自動開啟，所以需要照上面的步驟手動開啟一次。

## 怎麼改內容（全部在 `data.js`）

`data.js` 裡每一段文字都有 `ja`（日文）和 `zh`（繁體中文）兩個版本。改完存檔、commit、push 到 `main` 就會更新。
改完請先執行 `node --test`：少一個逗號或引號沒關好時，第一個測試就會失敗並指出行號；沒有漏掉某一種語言也會一起檢查。
（萬一壞掉的 `data.js` 被 push 出去，網站只會顯示字標與主視覺照片，不會出現空白的骨架，但其他內容都看不到。）

### 應援標語、首頁文字

`hero.slogan` 是首頁名字下方的那句話；`hero.eyebrow` 是名字上方的小字（這是什麼網站）。
標語用的是「給彩花的信」裡「はじめに／寫在前面」的第一句（文字和 `letter-data.js` 完全相同；網站主人 2026-11-11 確認沿用），要換成別句時直接改這兩行：

```js
slogan: {
  ja: '彩花ちゃんがいてくれるおかげで、ぼくの人生は、前よりもずっと彩り豊かで、幸せなものになりました。',
  zh: '因為有彩花，我的人生變得更有色彩，也更加幸福。'
},
```

句子裡有「、」「，」時，畫面上只會在逗號之後換行（文字本身不會被改動）。

### 個人資料

`profile` 陣列裡每一筆是一個欄位。有內容的欄位一定要寫出處（`sources`，代號對應最下面的 `sources` 清單，見「[資料來源](#資料來源sources)」）：

```js
{ label: { ja: '出身地', zh: '出身地' }, value: { ja: '東京都', zh: '東京都' }, sources: ['oricon-2020-profile'] },
```

- `value: null` 的欄位**不會顯示在網頁上**（資料留著，確認之後填入就會出現）。目前是 null 的：身高、興趣／專長。
  沒有可靠來源的資料（身高、體重、MBTI…）不要填推測值。
- `lang: 'ja'` 表示這一列的內容是日文原文（例如「自己紹介フレーズ」），中文版也照樣顯示日文。
- 「自己紹介フレーズ／自我介紹用語」是本人的自我介紹用語，不是官方職稱也不是暱稱；
  「NIZOOキャラクター」只寫哪個角色對應 AYAKA，角色自己的設定與喜好不是彩花本人的資料，不要寫進來。

### 興趣（個人資料下面的小區塊）

`hobbies.items` 一項一筆（名稱＋一兩句說明），`hobbies.sources` 是整塊共用的出處。
區塊上方的說明 `ui.hobbiesLead` 寫明是哪一次訪談（「2025 年 9 月訪談中分享的興趣」）：
只放有出處、有年月的內容，說明裡不要用「最近」，不同訪談的內容不要混在一起；清空 `items` 整塊就會隱藏。

### 年表

在 `timeline` 陣列加一筆。`date` 可以寫 `'2027-01-01'`、`'2027-01'` 或 `'2027'`，不確定日期就寫 `null`。
請照日期由早到晚排列，同一天不要有兩筆（同一天的事寫在同一筆的說明裡）。
`{ placeholder: true }` 是畫面上「之後會陸續補上」的空白欄位，不需要時可以刪掉。
`note` 裡寫 `\n` 會換行（例如兩句各一行）。

```js
{
  date: '2027-01-01',
  title: { ja: '出来事のタイトル', zh: '事件標題' },
  note:  { ja: '補足（不要なら空文字）', zh: '補充說明（不需要可留空）' },
  sources: ['出處代號'],        // 查來的資料一定要有；網站主人自己的經歷改寫 own: true
  link: 'love-yourself'         // 可省略：「作品」區某一首歌的 id，說明後面會出現「看作品介紹」的連結
},
```

年表只放查證過的事：每一筆都要有官方網站或新聞報導可以對照。專輯封面、雜誌封面等官方圖片不放，只用文字。

### 作品與訪談（`works`、`interviews`）

「作品とインタビュー／作品與訪談」區接在年表後面，只有文字與外部連結（不放官方照片、專輯封面、歌詞、MV 截圖，也不嵌入任何第三方元件）。

- **作品**（`works`）：一首歌一筆。`id` 是英文代號（網址錨點 `#work-代號`，年表的 `link` 也用它）、`members`、`release`（收錄作品與發行日）、
  `text`（一兩句介紹）、`official`（官方作品頁的出處代號）、`sources`（訪談等出處）。
  作詞一律寫「作詞に参加／參與作詞」或「共同作詞」，不要寫成一個人包辦，也不要寫成作曲。中文的成員名用「真子、彩花、梨久、未光」。
- **訪談摘錄**（`interviews`）：一則一筆，`title`、`text`（網站主人整理的短摘要）、`more`（同一篇的補充，可省略）、`sources`（一定要有媒體、日期、連結）。
  摘要不是逐字引用，不加引號冒充原話，也不要替本人創造沒說過的話或感受；不要把整篇訪談搬進來。
  提到「喜歡的歌」這類會變的事，一定要保留受訪的年月。

### 官方連結（`links`）

「關於本站」裡的「公式リンク／官方連結」。只放官方網站與本人帳號：`label`、`url`（https）、`handle`（帳號名稱，顯示在連結後面、不加底線）、
`sources`（確認帳號屬於本人的出處，會顯示成連結下面的一行小字）。

### 資料來源（`sources`）

`data.js` 最下面的 `sources` 是全站的出處清單。上面每一筆公開資料（個人資料、興趣、作品、訪談、年表、官方連結）都用 `sources: ['代號']` 指到它：

```js
'oricon-2025-09-12': { name: 'ORICON NEWS', url: 'https://www.oricon.co.jp/news/2406152/full/', published: '2025-09-12', checked: '2026-11-14' },
```

| 欄位 | 內容 |
| --- | --- |
| `name` | 來源名稱（媒體或網站）；日文和中文寫法不同時用 `{ ja, zh }` |
| `url` | 網址，一定是 `https://` |
| `published` | 刊登日期：`'YYYY-MM-DD'`、`'YYYY-MM'` 或 `'YYYY'`；官方網站的常設頁面、或沒有記下日期的報導寫 `null` |
| `checked` | 最近一次打開來源、核對內容的日期 |

新增資料的順序：**先打開來源確認內容 → 在 `sources` 加一筆 → 在資料上寫 `sources: ['代號']`**。來源和想寫的內容有出入時，照來源能直接支持的說法寫。
網頁上的呈現：個人資料與年表下方各有一個預設收合的「出典／資料來源」，展開後是「項目：來源（刊登日期）」的清單（出處相同的項目會合併成一列）；
作品與訪談的連結直接列在每一則下面。所有外部連結都在新分頁開啟，並加上 `rel="noopener noreferrer"`。
`node --test` 會檢查：每個代號都找得到、沒有用不到的出處、有內容的個人資料列與查來的年表都有出處、年表照日期排列且不重複。

### 應援留言

`messages` 目前是空的（`messages: []`）：原本的 4 則是範例文字，已經拿掉，「應援留言」區只放「給彩花的信」的入口小卡。

### 給彩花的信（`letter.html`，文字在 `letter-data.js`）

首頁「應援留言」區裡有一張入口小卡（「彩花ちゃんへの手紙／手紙を読む」），連到獨立的一頁 `letter.html`。信的文字全部在 `letter-data.js`：

- `heading`、`lead`、`salutation`：頁面標題、說明、宛名（「彩花ちゃんへ 🤍／給彩花 🤍」）。
- `sections`：信的各小節，順序就是網頁上的順序。每一節有 `id`（英文、不重複）、`heading`（小節標題）、`paragraphs`（段落，每段 `{ ja, zh }`）。
  需要時可加 `words`（當時準備過的日文，原文照放；中文版也保留日文並標 `lang="ja"`）、`paragraphsAfter`（放在 `words` 後面的段落）、
  `link`（連回首頁某區塊，例如 `{ href: 'index.html#gallery', label: { ja: '…', zh: '…' } }`）。
- 段落文字裡的 `\n` 是「換行」：同一段裡另起一行（段落和段落之間才有空白）。中文照網站主人原稿的分行，日文每一段的行數要和中文一樣（`node --test` 會檢查）。
- `words` 的每一句可以是一個字串，也可以拆成幾小塊的陣列（例如 `['いま、', 'じんせいで', 'いちばん', 'だいすきなのは', 'アヤカ！']`）：畫面上的字一模一樣，只是手機上要換行時會從塊和塊之間換，不會把「だいすき」拆成兩行。
- 信裡只寫歌名，不放歌詞（整個網站都一樣）。
- `signoff`、`signature`：結尾的日期與署名（「YU HONG より」）。
- 首頁入口小卡的四行字在 `data.js` 的 `ui.letterEntryEyebrow`、`ui.letterEntryTitle`、`ui.letterEntryText`、`ui.letterEntryCta`。

改完執行 `node --test`，會檢查每一段都有日文與中文、小節 `id` 不重複、連結是站內相對路徑、署名有「YU HONG」。
信頁的頁首只有品牌字標（連回首頁）與語言切換，沒有導覽列、也不固定在上方；語言設定和首頁共用。
信頁有 `<meta name="robots" content="noindex">`，不會被搜尋引擎收錄；想讓它被收錄時拿掉這一行即可。
列印這一頁時只會印出信本身（白底、沒有頁首頁尾）。

## 換照片

**新照片一律先用 `scripts/import_photos.py` 處理**：它會裁成 4:5 直式、去除 GPS／EXIF 等中繼資料，再存成 `photos/前綴-01.jpg`…。
`node --test` 會要求相簿每張照片都剛好是 4:5（容差 0.002），自己裁的圖很容易過不了。需要 Python 3 與 Pillow（`pip install Pillow`）。

1. 把新圖放在任一資料夾（檔名排序就是順序），裁切＋去除中繼資料＋產生 WebP 一次做完：

   ```bash
   python3 scripts/import_photos.py 來源資料夾 --prefix ayaka
   python3 scripts/make_images.py --match 'ayaka-*.jpg'
   ```

   活動照片用 `--prefix ayaka`，視訊回憶用 `--prefix call`；`--match 'ayaka-*.jpg'` 讓 `make_images.py` 只處理這一組。
   `import_photos.py` 預設固定上緣、只裁掉下方多餘的部分（`--anchor center` 可改成置中）。
   `make_images.py` 會為每張照片產生 `-480.webp`、`-800.webp`、`-1024.webp`、`-full.webp`；不加 `--match` 會處理全部 `photos/*.jpg`，並從 `photos/ayaka-07.jpg` 裁出 `photos/og.jpg`（分享預覽圖，想換來源請改腳本裡的 `OG_SOURCE`）。
   暫時不想處理 WebP 的話，把 `data.js` 的 `site.webp` 改成 `false` 即可。
2. 在 `data.js` 改照片資料：活動照片在 `photos` 陣列（`src`、`date`、`alt_ja`、`alt_zh`、`width`、`height`），視訊回憶在 `callPhotos.items`（日期是整組共用的 `callPhotos.date`）。首頁主視覺是 `hero.photo`。
3. 對照用的原始檔也一起更新：`photos/photos.json`（活動照片）、`photos/call-photos.json`（視訊回憶，`node --test` 會檢查它和 `data.js` 的 `callPhotos` 完全一致）。
4. 執行 `node --test`，會檢查照片檔案與 WebP 版本都存在、`width`／`height` 和 JPEG 實際尺寸一致、每張都是 4:5。

## 安全說明摘要

公開網站是純靜態、沒有後端、沒有表單、不收集任何資料，也不載入任何第三方資源。
每個頁面都有嚴格的 Content-Security-Policy，所有程式與樣式都放在獨立檔案，寫入畫面只用 `textContent`，
被別的網站用 iframe 嵌入時會隱藏內容、只留下開啟連結（GitHub Pages 無法設定 frame 相關標頭，所以無法完全禁止嵌入）。細節請看 [SECURITY.md](SECURITY.md)。

「合言葉のページ」（私密區）是另一個服務：密碼在伺服器驗證、照片與回覆存在 Cloudflare，公開網站只放一個連結，CSP 沒有因此改動。它的防護與測試寫在 [backend/README.md](backend/README.md#防護一覽)。

## 帳號安全建議

- GitHub 帳號開啟 **兩步驟驗證**：Settings → Password and authentication → Two-factor authentication（建議用 passkey 或 authenticator app，並保存 recovery codes）。
- Pages 設定勾選 **Enforce HTTPS**：Settings → Pages。
- 保護 `main` 分支（禁止 force push 與刪除）：Settings → Rules → Rulesets → New branch ruleset，目標 `main`，勾選「Block force pushes」與「Restrict deletions」。
- Settings → Emails：勾選「Keep my email addresses private」與「Block command line pushes that expose my email」，避免 commit 帶出個人信箱。
- 部署私密區之後，Cloudflare 帳號也請開啟兩步驟驗證：能登入那個帳號的人，就能直接讀到私密區的照片與回覆。
