# 合言葉のページ（私密區）的後端

這個資料夾是「合言葉のページ」的伺服器程式：知道合言葉（訪客密碼）的人可以打開一頁私人內容——標題、留言、照片——並留下文字回覆；回覆只會出現在站主自己的管理頁。

它和公開的應援網站是**兩個分開的東西**：

- 公開網站（repo 根目錄）照舊是純靜態網站，放在 GitHub Pages，沒有後端。
- 私密區（這個資料夾）部署在 Cloudflare Workers，另外一個網址。公開網站只放一個連到它的連結（`data.js` 的 `site.roomUrl`，還沒填時不顯示）。

> 2026-11-14 的需求更新：網站主人要求新增密碼登入、私人合照與訪客回覆，因此先前「不新增後端、登入或留言寫入」的限制，**只對公開網站繼續有效**；私密區是依這次需求新增的獨立服務。

**這個 repo 是公開的。** 這個資料夾裡只有程式、測試與合成的範例圖；正式的密碼、金鑰、照片、留言與回覆都只存在 Cloudflare 上（見「資料放在哪裡」），站主的信箱也不寫在任何檔案裡。

目前狀態（2026-11-16）：**兩個服務已部署並設定金鑰**（部署在站主自己的 Cloudflare 帳號，用的是 commit `2e02a12`）；**管理端的 Access／MFA 與正式環境驗收尚未完成，尚未匯入正式內容**。站主要做的事、方案與付款條件、部署順序整理在 [DEPLOY.md](DEPLOY.md)。接下來要先用範例文字與合成的測試圖通過「正式環境驗收」（[ACCEPTANCE.md](ACCEPTANCE.md)），**通過之後才匯入真正的合照**。（2026-11-15 交付這一版時：程式與測試完成，還沒有部署。）

## 整體架構

```
公開網站（GitHub Pages，純靜態）
   └─ 一行小字連結 ──▶ 訪客端 Worker「ayaka-room」（任何人都連得到，但沒有合言葉只看得到登入表單）
                           │  讀：標題、留言、照片      寫：登入狀態、回覆、限速計數
                           ▼
                  D1 資料庫「ayaka-room」＋ R2 儲存桶「ayaka-room-photos」（都沒有公開網址）
                           ▲
                           │  讀寫全部
                  管理端 Worker「ayaka-room-admin」
                           ▲
                  Cloudflare Access（登入＋第二因子）◀── 站主
```

- **兩個 Worker、兩個網址**。訪客端只有「看專區、送出回覆、登出」的程式；讀取回覆、管理照片、換密碼的程式只存在管理端。拿訪客的登入去敲管理端，什麼都拿不到。
- **管理端整個放在 Cloudflare Access 後面**，管理者的登入完全交給 Access；Worker 收到請求後再確認一次身分（見下）。
- 兩個 Worker 共用同一個資料庫與儲存桶，但訪客端的程式裡沒有任何讀取回覆或修改內容的查詢。

## 資料放在哪裡

| 資料 | 位置 | 說明 |
| --- | --- | --- |
| 合言葉（訪客密碼） | D1 `settings` | 只存 `HMAC-SHA-256(PEPPER, 密碼)`。資料庫裡沒有密碼本身；新密碼只在產生的那一次顯示在管理頁 |
| 寫到一半、還沒送出的回覆 | 只在訪客那一頁的輸入欄裡 | 不寫進瀏覽器的儲存空間（localStorage 等），伺服器也不存；登入過期時只在那一次的請求與回應之間來回 |
| 訪客的登入狀態 | D1 `sessions` | 只存登入憑證的 SHA-256。憑證本身只在訪客瀏覽器的 cookie 裡 |
| 標題、留言、照片說明 | D1 `settings`、`photos` | 由管理頁編輯；登入後才讀得到 |
| 照片（原圖與縮圖） | R2 `photos/<編號>/full.jpg`、`thumb.jpg` | 儲存桶不開公開存取；只能經由 Worker、通過登入檢查後取得 |
| 訪客的回覆 | D1 `replies` | 純文字。只有管理端讀得到 |
| 限速計數 | D1 `rate_limits` | IP 只存加了金鑰的雜湊，不存原始 IP |
| 管理紀錄 | D1 `audit` | 只記「做了什麼、什麼時候」，不記密碼、憑證或回覆內容 |
| 金鑰 `PEPPER`、`SESSION_SECRET` | Cloudflare 的 secrets | 部署時用 `wrangler secret put` 設定，不在 repo、不在資料庫 |
| Access 的設定值、站主信箱 | Cloudflare 的 secrets | `TEAM_DOMAIN`、`POLICY_AUD`、`ADMIN_EMAILS`，同樣不寫進檔案 |
| 管理者的登入 | Cloudflare Access | 這裡的程式不處理、也不儲存任何管理者密碼 |

repo 裡**有**的：程式、資料表結構（`migrations/`，沒有資料）、測試、合成的範例圖（`tests/fixtures/`，寫著 SAMPLE 的漸層圖卡）。
repo 裡**沒有**的：以上表格的任何一項實際內容。`.gitignore` 排除了 `.dev.vars`、`.env`、`.wrangler/` 等本機檔案，測試也會檢查。

## 誰可以做什麼

**訪客（知道合言葉的人）**

1. 在登入表單貼上合言葉（8 組、每組 4 個十六進位字）。大小寫、空白、連字號、全形半形都不影響；連引號或句號一起複製到也可以。
2. 伺服器比對成功後，發一個有期限的登入 cookie（預設 7 天）。之後每一次取得頁面、縮圖、原圖、送出回覆，伺服器都重新檢查這個登入是否還有效。
3. 可以看專區、放大照片、送出純文字回覆（最多 2000 字，不需要名字或 email）、登出。
   寫到一半登入過期的話，內容會留在頁面上：可以先複製，再在同一頁重新輸入合言葉，不用離開頁面（見「防護一覽」的「寫到一半的回覆」）。
4. **不能**讀任何回覆（包含自己送出的）、不能修改或刪除任何東西。訪客端沒有這些網址。

持有同一組合言葉的人權限都一樣。網站**不會**、也無法知道對方是誰：管理頁會把回覆標示為「來自持有訪客密碼的人，身分未經驗證」，不會標成「彩花本人」。

**站主（管理者）**

- 經由 Cloudflare Access 登入後進入管理頁：收件匣（看、刪除、匯出 JSON）、照片（上傳、改說明、排序、刪除）、標題與留言、密碼與登入（產生合言葉、撤銷所有登入、清除限速紀錄、管理紀錄）。
- 管理者的登入要兩個步驟：Access 的登入方式，加上 Access 自己要求的第二因子（驗證器 App 或安全金鑰）。怎麼設定、怎麼確認真的有強制，見「[管理端的多因素驗證（MFA）](#管理端的多因素驗證mfa)」。
- 管理端對每個請求都做兩層確認：先是 Cloudflare Access 擋在前面；Worker 自己再確認「這個請求真的通過了 Access、對象（AUD）是這個應用程式、信箱在 `ADMIN_EMAILS` 裡」。身分來源有兩種，都接受：
  - `ctx.access`：把 Access 直接掛在 Worker 上時，平台提供的已驗證身分。
  - `Cf-Access-Jwt-Assertion` 標頭：以網址為單位的 Access 應用程式附上的簽章憑證，用 `jose` 驗證簽章、發行者、期限、對象。
- 任何一項不符、或設定沒填好，回 `403 Forbidden (原因代碼)`。原因代碼是給站主排查設定用的（例如 `not-configured`、`aud-mismatch`、`not-allowed`），不含私人內容。

## 防護一覽

| 項目 | 做法 |
| --- | --- |
| 密碼驗證 | 只在伺服器。瀏覽器裡沒有任何「已登入」的旗標；改 localStorage、塞假 cookie 都沒有用 |
| 密碼的儲存 | `HMAC-SHA-256(PEPPER, 正規化後的密碼)`。合言葉只有一種來源：管理頁用系統的亂數產生器（CSPRNG）取 16 個位元組（128 bit），寫成 8 組十六進位字。**沒有自己取密碼的入口**；登入時也只受理這個格式，資料庫裡就算有別種密碼的雜湊也登不進來。貼上時的整理（大小寫、空白、連字號）不會減少這 128 bit。用 HMAC 而不是 bcrypt／Argon2 這類刻意算得很慢的雜湊，前提就是「密碼是隨機產生的 128 bit，不是人取的字」；將來如果要讓人自己取密碼，必須換成合適的密碼雜湊（KDF），並在正式環境量過 CPU 用量之後才能開放。`PEPPER` 是部署平台的 secret，只拿到資料庫的人沒有它。這些是設計上的前提，不是「不可能被猜中」的保證（`shared/password.js` 開頭有完整的說明） |
| 登入 cookie | `__Host-room-session`：`Secure`、`HttpOnly`、`SameSite=Lax`、`Path=/`、沒有 `Domain`、`Max-Age` 7 天（`SESSION_TTL_SECONDS` 可調，最長 30 天）。值是 256 bit 的隨機憑證。另外兩個 cookie（登入表單的防偽造編號、語言）也都是 `__Host-`、`Secure`、`HttpOnly` |
| 登入失效 | 登出刪除那一筆登入；換密碼讓所有舊登入失效；「撤銷所有登入」不換密碼也能全部登出；過期由伺服器判斷（不靠瀏覽器刪 cookie）。登入後在背景做的清理只刪「過期」或「以刪除當下資料庫裡的密碼版本來看已經失效」的登入，不會用先前讀到的舊版本去比 |
| 限速（伺服器端，存在資料庫，全球一致） | 登入：同一個 IP 10 分鐘內錯 5 次就擋到時間窗結束，所有來源合計 1 小時 200 次。回覆：同一次登入 10 分鐘 5 則、一天 30 則，同一個 IP 一天 60 則，所有人合計一天 200 則（`REPLY_DAILY_CAP` 可調）。做法是「先累計、再判斷」，同時送出一大批請求也不會超過上限。被擋時回 `429` 與 `Retry-After` |
| 輸入限制 | 密碼 200 字、回覆 2000 字（表情符號算一個字）。請求的內容用串流一塊一塊讀，**讀到上限就停止並回 `413`**，不會先把整個內容讀進記憶體再檢查；`Content-Length` 只用來提早拒絕（對方可以不送或亂寫）。上限：登入與回覆 32 KB、登出 4 KB、管理端的表單 64 KB、照片上傳約 4.7 MB（原圖 4 MB＋縮圖 600 KB＋說明文字）。只接受一般表單格式；控制字元會被去掉 |
| 寫到一半的回覆 | 送出期間輸入欄鎖住（唯讀）、按鈕停用；只有伺服器確認存好、而且輸入欄裡仍然是送出去的那一份內容時才清空（等待期間內容如果變了，就留著並說明「這些還沒有送出」）。30 秒沒有回應當作沒有收到確認，內容留著。沒有收到「已經存好」的確認時（斷線、逾時、伺服器錯誤、登入過期、表單過期），畫面上說的是「無法確認有沒有送出、內容還留著、可以繼續送出」，不說「沒有送出」——那一則有可能其實已經存好。登入過期時內容留在頁面上，可以複製，也可以不離開頁面重新登入後再送；頁面上的防偽造編號過期時（例如在另一個分頁重新登入過）會自動換新的再送一次。沒有 JavaScript 時，草稿跟著登入表單走，登入成功後回到回覆的輸入欄。草稿與合言葉不寫進 localStorage 等瀏覽器的儲存空間，伺服器也不存草稿 |
| 回覆重送不會重複 | 回覆表單裡有一個**送出編號**（欄位 `nonce`），代表「這一則回覆」，和登入無關。伺服器用「送出編號＋內容」認出同一次送出（資料表的唯一條件保證只存一筆）：其實已經存好、只是成功的回應沒有送到頁面的那一則，之後再按幾次、中間登入過期後重新登入、在另一個分頁重新登入過、或沒有 JavaScript 時草稿跟著登入表單往返，都只會有一筆。重新登入與 `/session` 只換防偽造編號，不發新的送出編號；伺服器確認存好之後頁面才拿到下一個，所以下一則就算文字完全一樣也是新的一則（不是只比內容）。每一次寫入都先檢查登入狀態與防偽造編號，通過了才去重與寫入；送出編號不是權限，知道它也不能做任何事 |
| 跨站偽造請求（CSRF） | 所有 POST 都要求 `Origin` 等於本站、`Sec-Fetch-Site` 是 `same-origin`（瀏覽器有送的話），再加上防偽造編號：登入前用 cookie＋表單的雙重送出，登入後用和登入狀態綁在一起的編號（重新登入就換新的）。它和回覆的送出編號是兩個各自獨立的編號。GET 不會改變任何狀態 |
| 文字輸出 | 所有動態文字都經過 `escapeHtml` 才放進頁面；訪客寫的 HTML 只會顯示成文字。每個回應都有嚴格的 CSP（`default-src 'none'`，只允許同站的樣式、腳本、圖片；沒有 inline 程式或樣式） |
| 資料庫 | 全部用參數綁定（`prepare().bind()`），沒有把輸入接進 SQL 字串 |
| 快取 | 每個回應都是 `Cache-Control: private, no-store`；不使用 Cloudflare 的快取 API，也不啟用 Workers Caching |
| 照片 | R2 儲存桶不開公開存取、不接自訂網域；每次取圖都檢查登入。沒登入一律 `401`（不論那張照片存不存在） |
| 照片的中繼資料 | 上傳時瀏覽器先重新編碼（縮小、依拍攝方向轉正）。伺服器這一層不依賴那一步：不論檔案是誰產生的，都把整個檔案的結構走過一遍，照白名單重新排出一份——只留量化表、霍夫曼表、影像格式、掃描資料；JFIF 檔頭一律重寫成固定的 18 個位元組（內嵌的縮圖、檔頭後面多塞的資料、解析度欄位都不帶過去）；Adobe 色彩標記只留「色彩轉換方式」一個值；其餘（Exif 的拍攝地點／裝置／時間、XMP、ICC、IPTC、MPF、JFXX、註解、填充位元組、檔尾多餘的資料與接在後面的第二張圖）都不寫進儲存空間。表格長度對不上、不認得的標記、瀏覽器不支援的編碼（CMYK、12 bit、算術編碼…）整個檔案不收。這是無損的處理（影像的壓縮資料原封不動）；也因為不解碼影像，伺服器看不到「藏在壓縮資料或畫面裡」的東西，那一層由上傳前的重新編碼負責 |
| 設定不完整或服務出錯 | 一律拒絕：金鑰沒設定 → 整個服務回 `503`；資料庫查詢失敗 → `500`，不給內容；Access 沒設定好 → `403` |
| 日誌 | 程式只記事件名稱（例如 `login_failed`、`reply_saved`），不記密碼、憑證或回覆內容；設定檔關閉了 Workers 的日誌收集（`observability.enabled: false`） |
| 搜尋引擎 | 每個回應都帶 `X-Robots-Tag: noindex, nofollow, noarchive` |

### 四層防護各自是什麼、現在的狀態

「防火牆」其實是四件不同的事，各自擋的東西不一樣，目前的狀態也不一樣：

| 層 | 誰提供、在哪裡設定 | 現在的狀態 | 擋什麼／不擋什麼 |
| --- | --- | --- | --- |
| 1. 平台的基礎防護 | Cloudflare 的網路本身。依官方文件，L3／L4／L7 的 DDoS 防護對所有方案與服務自動提供；`workers.dev` 網址被當作免費方案的網站看待 | 不需要我們設定；**這個專案沒有驗證過它**（也無從在本機驗證） | 處理的是大量的攻擊流量。它不認識我們的登入，不會替我們擋「拿到合言葉的人」、慢慢猜密碼、或把每天的請求額度用完 |
| 2. Cloudflare Access（含第二因子） | Zero Trust 後台，由站主設定 | **還沒有設定**（2026-11-16：兩個服務已部署，Access 還沒設定）。只用在管理端，所有路徑。設定與驗收見「管理端的多因素驗證（MFA）」 | 擋的是沒有通過站主登入＋第二因子的人進管理端。訪客端不在它後面 |
| 3. 應用程式自己的限速 | 我們的程式，計數存在 D1 | **已實作，已在本機測試**（上表「限速」那一列） | 擋密碼亂猜與灌回覆。計數的是「送到 Worker 的請求」，所以擋不了把 Workers 每天的請求額度用完這件事 |
| 4. 自訂的 WAF 規則／WAF 限速規則 | Cloudflare 後台，設在自己的網域上 | **一條都沒有設定**。這類規則要先把 Worker 接到自己在 Cloudflare 上的網域才有地方設；現在兩個 Worker 只有 `workers.dev` 網址 | 之後如果遇到惡意流量、或想在請求到達 Worker 之前就擋掉，再考慮接網域來設定 |

真正擋住未授權存取的是 Worker 自己的檢查（兩個服務都是）；Access 是管理端前面多加的一層，負責管理者的登入與第二因子。

### 其他入口與繞過的可能

| 項目 | 實際情況 |
| --- | --- |
| Preview URLs（預覽網址；新版後台也叫 Version URLs） | 兩個 Worker 的設定檔都寫了 `preview_urls: false`。預覽網址是同一支程式的另一個入口：訪客端從哪個網址進來都一樣要驗證；管理端如果 Access 是掛在 Worker 上，預覽網址也在保護範圍內，如果是以 `workers.dev` 網址為單位設定的，預覽網址不在範圍內——所以直接關掉，並在部署後確認（後台，或 `check_deployed.mjs --preview-url`） |
| 來源伺服器 | 沒有。程式直接跑在 Cloudflare 上，沒有「繞過 Cloudflare 直連來源」這條路。D1 與 R2 只能經由 Worker 的綁定、或站主的 Cloudflare 帳號（API）存取 |
| R2 的公開網址 | 預設關閉；不要開啟 `r2.dev` 公開網址，也不要接自訂網域。部署後用 `wrangler r2 bucket dev-url get` 與 `wrangler r2 bucket domain list` 確認 |
| Access 的政策 | 管理端的 Access 應用程式只放一條 Allow 政策（站主的信箱）。Bypass 政策放進來的請求沒有 Access 的憑證、Service Auth 的憑證沒有信箱，Worker 自己都會拒絕；但「Allow 政策卻沒有要求第二因子」Worker 看不出來，只能靠 Access 的設定與實際登入測試 |
| 其他入口 | 之後如果替 Worker 加自訂網域或路由：訪客端沒有影響；管理端要確認新網址也在 Access 的範圍內（Access 掛在 Worker 上時會自動涵蓋）。不管怎樣，管理端的 Worker 自己還會再驗一次身分 |

## 本機預覽與測試

需要 Node.js 22 以上、Python 3（產生樣式用）。瀏覽器測試與截圖另外需要 Playwright（在 repo 根目錄 `npm install`）。

先安裝（照 `package-lock.json` 的版本裝 wrangler 與 jose；不執行任何安裝腳本）：

```bash
cd backend
npm ci --ignore-scripts
```

之後在 `backend/` 裡可以用的指令（指令區塊與表格裡只有指令：macOS 預設的終端機 zsh 不會把指令後面的 `#` 當成註解）：

| 指令 | 作用 |
| --- | --- |
| `npm run dev` | 本機預覽：印出訪客端、管理頁的網址與一組測試用的合言葉；Ctrl+C 結束 |
| `npm test` | 全部測試（約 4 分鐘） |
| `npm run test:unit` | 單元測試（幾秒，不啟動任何服務） |
| `npm run test:roomjs` | 訪客頁面腳本的測試（不開瀏覽器：回應晚到、登入過期時草稿不會丟） |
| `npm run test:store` | 資料庫層的測試（本機的 D1：背景清理與換密碼交錯執行） |
| `npm run test:acceptance` | 驗收測試：對本機跑起來的兩個服務送真的 HTTP 請求 |
| `npm run test:failclosed` | 故意把設定弄壞，確認服務什麼都不給 |
| `npm run test:check` | 「部署後檢查」腳本自己的測試（含一個故意做錯的假服務） |
| `npm run test:browser` | 用瀏覽器實際操作（手機大小的畫面） |
| `npm run screenshots` | 產生審查用的截圖（預設放在 `backend/.local/screenshots/`） |
| `npm run build` | 公開網站的 `styles.css`、`backend/styles/` 或 `admin/client/` 改過之後，重新產生樣式與管理端的靜態檔 |

- 本機的服務用 `wrangler dev` 啟動（執行引擎 workerd 和 Cloudflare 正式環境相同），資料庫與儲存桶是本機的模擬。金鑰、合言葉、管理者身分都是每次執行時隨機產生的測試值。
- 測試環境啟動每個服務時，會等 `wrangler` 自己印出「Ready on …:<連接埠>」而且連接埠和要求的一致才算啟動；連接埠被別的程序搶先用掉時會換一組重來（只看「有沒有回應」的話，偶爾會把別的服務誤認成剛啟動的 Worker）。
- 管理頁在本機沒有真的 Cloudflare Access：測試用一個「模擬 Access」的小服務代替（自己簽憑證、提供公鑰），或用 wrangler 內建的 `access.dev` 模擬 `ctx.access`。這兩種模擬只在本機成立：Worker 只在 `ENVIRONMENT=local` 時才接受 `http://127.0.0.1` 的團隊網域，正式的設定檔裡不可以有 `ENVIRONMENT` 或 `access.dev`（測試會檢查）。
- 請用 Chrome、Edge 或 Firefox 開本機預覽。Safari 不接受 `http://localhost` 上的 `Secure` cookie，會登不進去（正式環境是 https，沒有這個問題）。
- `wrangler dev` 是開發工具：預設會在同一個連接埠多開一組不需要登入的「檢視本機資料」網址（`/cdn-cgi/local/explorer/…`）。測試與 `npm run dev` 已經把它關掉（`X_LOCAL_EXPLORER=false`），部署到 Cloudflare 之後也不存在；但請不要用通道工具把本機預覽公開到網路上。
- 用已安裝的 Chrome 跑瀏覽器測試：`QA_CHROME_PATH=/path/to/chrome npm run test:browser`。沒有安裝 Playwright 時，瀏覽器測試會全部略過（其餘照跑）。
- 不需要瀏覽器的測試（`unit`、`roomjs`、`store`、`acceptance`、`failclosed`、`check`）共 122 項；瀏覽器測試 19 項。`wrangler` 的本機工具啟動時可能會試著連到 `workers.cloudflare.com` 取一份模擬用的資料，連不上也不影響測試。

| 伺服器怎麼用 | 每次寫入都先驗證（連同登入狀態）；沒過就不往下做 | 和內容一起算出去重的識別：`SHA-256("reply:" + 送出編號 + ":" + 內容)`，不含登入代號 |

- 重新登入的回應與 `/session` 現在只給防偽造編號；頁面上也只有一個地方會換送出編號（收到「已經存好」之後）。兩邊各自成立：就算伺服器的回應裡多帶了一個編號，頁面也不會採用（`roomjs` 有測）。
- 沒有 JavaScript 時，登入過期後草稿放在登入表單裡，它的送出編號也跟著放在同一個表單（隱藏欄位），登入成功後兩者一起回到回覆的表單。格式不對的編號不會被放回頁面。
- 同樣的文字要送第二則，只要是「下一則」就可以：伺服器確認存好之後才發下一個送出編號，所以不是「全文相同就擋」。
- 去重的識別不分登入、也不分是誰送的，這是刻意的（重新登入之後就是另一次登入，伺服器沒有別的辦法認出「同一位訪客」）。送出編號是 128 bit 的隨機值，只出現在那位訪客自己的頁面裡。就算有人拿到別人的送出編號，要讓對方的回覆被當成「已經存過」，他得自己先把一模一樣的內容存進去——那段內容還是到了站主手上；內容只要有一個字不同，就是另一筆。
- 順序沒有變：登入狀態 → 防偽造編號 → 送出編號的格式與內容 → 去重 → 限速 → 寫入。沒登入、或防偽造編號不對的請求，就算那一則其實已經存過，也不會被回報成功（`acceptance` 有測）。
- 除了針對 Codex 重現的那條路寫的測試，另外有一個「隨機安排順序」的測試：用固定的亂數種子，把「送出（收到回應）」「送出（成功的回應沒收到）」「登入在別處被登出」「重新登入」「另一個分頁重新登入」「改內容」隨機排成幾條路，最後比對資料庫裡的回覆是不是剛好等於「不同的（送出編號＋內容）」各一筆。頁面腳本也有一個同樣做法的測試（`roomjs`）：隨機安排使用者的操作與伺服器的各種回應，確認送出編號只在「確認存好」之後才換、內容只在那時候才清空。拿修正前的程式跑，這兩個測試都會失敗。
- 做不到的：**重新整理或重新開啟頁面之後，頁面拿到的是新的送出編號**（草稿與編號都不寫進瀏覽器的儲存空間）。前一次如果其實已經存好，重新整理後再打一次同樣的內容會是第二則。

**2. 部署後檢查：不確定就是「無法判定」。**

- `--preview-url`、`--r2-url` 現在**只會回報「沒通過」或「無法判定」，不會回報「通過」**。連得到這個專案的 Worker（看回應的標頭或內容，不管狀態碼）、被轉到 Cloudflare Access、不用登入就拿到圖片 → 沒通過。其他任何回應——被限速（429）、伺服器錯誤（5xx）、沒有驗證過的轉址（3xx）、被拒絕（401／403）、找不到（404）——都是無法判定。
- 為什麼連「找不到」也不算通過：網址裡的版本編號不存在、或網址打錯時，回應也是找不到，單憑一次回應分不出來。「已經關閉」以後台或 `wrangler` 看到的設定為準（ACCEPTANCE.md 的 B-2）。
- 轉址不跟隨（每個網址只送一個請求），留給人用瀏覽器確認。
- 這一輪改的是「會被誤判成通過」的地方。其餘項目（例如「沒登入時照片網址回 401」「首頁只有登入表單」）要求的是明確的結果，遇到任何不符合的回應——包含 429 與 5xx——仍然記為沒通過，沒有改成無法判定：這是保守的方向，而且「回應裡有沒有不該出現的內容」要照樣檢查，不適合因為狀態碼就略過。遇到時重跑一次即可。
- 同一類的問題另外找到三處，一併修正：「開發工具的檢視網址不存在」原本是「不是 200 就通過」，「換密碼後舊密碼不能登入」原本是「沒登入成功就通過」——被限速或伺服器錯誤時都會被算成通過；「錯太多次會被限速」原本只要後面都是 429 就通過，連第一次嘗試就是 429（這個 IP 本來就在限速中，或是平台在擋）也算。現在第一項要明確的拒絕（400、401、403、404、405、410）、第二項要 401（密碼不對）、第三項要先看到「密碼不對」之後才開始被擋，才算通過；其餘是無法判定。
- 為了確定沒有漏掉同一類的地方，加了兩個整體的測試：（一）讓整個服務對任何請求都回同一種回應（500、502、503、429、轉址、不相干的頁面），檢查腳本不可以有任何一項通過；（二）對每一種故意做錯的假服務，輪流讓「第 k 個請求」改回 503 或 429（每個位置都試，共 1,898 種情況），原本抓得到的問題不可以因此被判成通過。第三處（限速）就是（一）找出來的。

**3. CPU 報告：缺資料不算通過。**

- 每一筆請求的 `cpuTime` 要是有限、不是負數的數字才算有效；不拿 `wallTime` 代替。
- 判定的順序：有請求達到或超過上限、或被平台以「超過 CPU 上限」中止 → 沒通過；否則只要有任何一筆收到的請求缺少有效數值 → 無法判定；都有數值而且都在上限以內 → 通過。
- 每一種操作顯示「有效量測數／總請求數」，缺資料的那一列標示無法判定。
- 另外加了 `--expect visitor｜admin`：要求那個 Worker 的每一種主要操作（和 ACCEPTANCE.md 的 B-4 同一組）都至少有一筆有效的量測，還沒量到的列出來，結果是無法判定。不加的話，報告會說明它沒有核對涵蓋範圍。
- `--limit` 不是大於 0 的數字時不會開始統計（原本那種情況每一筆都會被算成「沒超過」）。

另外，審查用的截圖腳本（`scripts/screenshots.mjs`）改成等圖片解碼完、畫到畫面上才截圖（放大的照片也一樣），圖片沒載入時會直接失敗。上一輪交付的截圖裡，深色模式的整頁那一張是在最後一張範例圖畫出來之前截的；頁面本身沒有問題。

## 管理端的多因素驗證（MFA）

管理頁看得到所有回覆與照片，所以管理者的登入要兩個步驟，而且第二個步驟要由 Cloudflare Access **強制**——不是「我用的帳號本來就有兩步驟」。

### 選用的做法：Access 的 independent MFA

Cloudflare Access 可以在登入方式之外，自己再要求一個第二因子（驗證器 App 的一次性密碼、安全金鑰、或裝置的生物辨識），不依賴登入用的那個帳號。官方文件把它叫 independent MFA，分三層設定：

| 層 | 在哪裡設定（依官方文件的名稱；後台實際的字樣以看到的為準） | 這個專案要設成什麼 |
| --- | --- | --- |
| 組織 | Zero Trust → Access controls → Access settings → **Allow multi-factor authentication (MFA)** | 勾選要允許的方法（Authenticator application；有安全金鑰的話加上 Security key），設定 **Authentication duration**，儲存。這一層沒開，下面兩層就沒有東西可以選。**Apply global MFA settings by default** 建議也打開：帳號下之後新增的 Access 應用程式預設都會要求第二因子 |
| 應用程式 | Zero Trust → Access controls → Applications → 管理端那一個 → Edit → Authentication → **MFA** 分頁 | 選 **Custom MFA settings**，**Authentication duration** 選 **Require every login**（每次登入 Access 都要第二因子）。不可以是 **Disable MFA** |
| 政策 | Zero Trust → Access controls → Policies → 管理端的那一條 Allow 政策 → Edit → **Multi-factor authentication (MFA)** | **Custom MFA settings** 或 **Respect global enforcement setting**。不可以是 **Disable MFA** |

**覆蓋關係：政策 ＞ 應用程式 ＞ 組織。** 下層有明確設定時，蓋過上層。所以：

- 應用程式選了 Custom MFA settings、政策卻選 Disable MFA → 結果是**不需要**第二因子（政策贏）。
- 應用程式與政策都選 Respect global enforcement setting → 看組織那一層有沒有打開 Apply global MFA settings by default；沒打開就是不需要。
- 所以三層都要看，而且最後要用實際登入來確認（下面的驗收）。

註冊驗證器：登入 `https://<團隊名稱>.cloudflareaccess.com`，在 Account → MFA devices → Add an MFA device 新增（官方文件也給了直接的網址 `…cloudflareaccess.com/AddMfaDevice`）。**驗證器 App（TOTP）每個人同時只能註冊一個**；安全金鑰與裝置的生物辨識可以註冊多個。所以備用請註冊**另一種**方式（組織層要先允許那一種方法）。註冊之後，請在 MFA devices 的清單裡確認它真的在上面，再把應用程式設成每次登入都要第二因子。

全部遺失時：用 Cloudflare 帳號到後台 Zero Trust → Team & Resources → Users → 該使用者 → MFA devices → Delete，刪掉之後重新註冊。這條路要靠 Cloudflare 帳號本身的登入，所以帳號的兩步驟驗證與備用碼要保管好。

### 不算數的

下面這些都只是「第一個登入步驟」那一邊的事，Access 並沒有因此要求第二因子，**不可以當成管理端 MFA 已經完成**：

- 登入用的 Google 或 GitHub 帳號自己有開兩步驟驗證。
- Cloudflare 帳號有開兩步驟驗證（那是保護後台，不是保護管理頁的登入）。
- 寄到信箱的一次性驗證碼（One-time PIN）。它是一種登入方式，只有一個因子。
- 用 Cloudflare 帳號登入（建立 Zero Trust 組織時預設的登入方式）。它同樣只是第一個步驟。

（Access 另外有一種「要求登入方式回報用了 MFA」的政策規則，官方文件說只支援 Okta、Microsoft Entra ID、OIDC 與 SAML 這幾種登入方式；個人用的 Google、GitHub、信箱驗證碼不適用，所以這裡不用它。）

### 必要驗收：沒有完成第二因子，進不了管理端

正式照片匯入之前一定要做，結果記在 ACCEPTANCE.md：

1. 開一個無痕視窗，打開管理端的網址。應該被轉到 `<團隊名稱>.cloudflareaccess.com` 的登入頁。
2. 完成第一個登入步驟（信箱驗證碼或 Google／GitHub）。
3. 出現第二因子的畫面時，**不要完成**，分別試：
   - 輸入錯的驗證碼 → 應該被拒絕，看不到管理頁。
   - 不輸入，直接在網址列再打開一次管理端的網址（以及 `/photos`、`/export.json`）→ 應該還是停在 Access，看不到管理頁、也下載不到任何東西。
4. 這時候在另一個終端機開著 `npx wrangler tail ayaka-room-admin` 看：不應該出現任何成功（200）的請求。
5. 完成第二因子 → 這時才看得到管理頁。
6. 登出（管理頁右上角）後重新打開 → 又要兩個步驟。
7. 到 Zero Trust 後台看 Access 的登入紀錄，把看得到的記下來。輸入錯的驗證碼不一定會留下紀錄（見下面「文件上查不到」），看不到那幾次時不代表第二因子沒有擋住——以第 3、4 步實際看到的為準。

第 3 步只要有任何一種情況看得到管理頁，就表示第二因子沒有被強制：回頭檢查三層設定，修好之前不要放真正的內容。

### 文件上查不到、要實際確認的

- **這個功能在 Zero Trust Free 方案能不能用**：官方的 independent MFA 說明、Access 的更新紀錄（2026-04-15 的項目）、方案比較頁都沒有寫它屬於哪個方案（2026-11-15 查閱）。Cloudflare 社群論壇上有使用者回報在 Zero Trust Free 上用驗證器 App 的 independent MFA，錯的驗證碼會被拒絕——那是使用者的回報，不是官方的說法，所以仍然以站主自己後台的實測為準。開通之後如果找不到上面的設定、設定存不起來、或驗證器註冊不上去，請停在這裡——管理端沒有強制的第二因子之前，不要匯入真正的照片。接下來的順序：先核對組織、應用程式、政策三層的設定，以及登入的身分與所在的組織；還是不行，就向 Cloudflare 官方確認這個帳號與方案能不能使用這個功能（Free 方案的支援管道是社群論壇與 Discord，Pay-as-you-go 才有客服單）；官方確認付費方案確實能解決之後，才由站主決定要不要升級（Pay-as-you-go 是每人每月 7 美元）。**升級不是已知的解法**：沒有確認之前，付了費也不保證能用。不靠方案的另一條路是在管理端的程式裡自己加第二因子，那需要另一輪開發與審查（步驟在 [DEPLOY.md 的階段 5](DEPLOY.md#階段-5管理端的-access-與第二因子)）。
- **一開始看不到完整的設定，不代表不能用**：同一批使用者回報提到，所有方法都關閉時，後台不顯示「Apply global MFA settings by default」與驗證的有效時間，應用程式那一層的 MFA 選項也是隱藏的。先在組織層勾選方法並儲存，再看其他設定有沒有出現（這一點還沒有實測）。
- **輸入錯的驗證碼會不會留下紀錄**：有使用者回報，錯的驗證碼被拒絕了，但在 Access 的登入紀錄與 API 裡找不到對應的失敗事件。所以驗收不靠登入紀錄來證明「有擋住」。
- **註冊顯示成功、清單裡卻沒有裝置**：有使用者回報遇過這個情況。註冊之後請看一眼 MFA devices 的清單。
- **還沒註冊驗證器的人第一次登入會看到什麼**（直接引導註冊，還是被擋下）：文件沒有寫，以實測為準。
- **Worker 沒辦法自己再確認一次**：官方文件列出的 Access 憑證欄位（`aud`、`email`、`exp`、`iat`、`nbf`、`iss`、`type`、`identity_nonce`、`sub`、`country`）裡，沒有「這次登入有沒有完成第二因子」的欄位。所以管理端的程式能確認的是「經過了 Access、是這個應用程式、信箱是站主」，第二因子有沒有生效只能靠上面的設定與實測。部署後可以看一次實際的憑證內容；如果有穩定的欄位可以用，再評估要不要加進程式。

## 部署之後的檢查

先把三個值設成變數（`<…>` 換成實際的值），下面的指令在同一個終端機視窗裡執行：

```bash
VISITOR=https://ayaka-room.<你的子網域>.workers.dev
ADMIN=https://ayaka-room-admin.<你的子網域>.workers.dev
TEAM=<團隊名稱>.cloudflareaccess.com
```

1. 不需要密碼的檢查（部署完就可以跑）：

   ```bash
   node scripts/check_deployed.mjs --visitor "$VISITOR" --admin "$ADMIN" --team-domain "$TEAM"
   ```

2. 放進範例內容之後：用合成測試圖的真實編號，檢查同一個圖片網址在各種狀態下的存取結果，並確認留言入庫。測試圖的編號寫在管理頁「照片」那一頁每張照片下面；密碼在執行時輸入，不會顯示：

   ```bash
   node scripts/check_deployed.mjs --visitor "$VISITOR" --admin "$ADMIN" --team-domain "$TEAM" --photo-id <測試圖的編號> --reply --report ~/ayaka-room-acceptance-report.json
   ```

每一項的結果有三種：`✔` 通過、`✖` 沒通過、`？` **無法判定**。無法判定不算通過——例如連不上、被限速（429）、伺服器錯誤（5xx）、轉到沒有驗證過的地方、沒有提供判斷需要的資訊、或需要人去管理頁按按鈕而這一次沒有做。結束代碼：0＝全部通過，1＝有沒通過的，2＝沒有失敗但有無法判定的。

它檢查什麼：

- **不用密碼**：首頁只有登入表單、照片網址回 401、偽造的 cookie 沒有用、回應的標頭、訪客端沒有管理用的網址；用 `http://` 連線會轉到 `https://`（連不上時是「無法判定」，不會算成通過）；管理端的每個網址都被擋下，而且是轉到**預期的團隊網域**（解析轉址網址的主機名稱來比對，不是看網址裡有沒有出現那幾個字；沒有給 `--team-domain` 時這一項是無法判定）。
- **`--photo-id`（需要測試階段的訪客密碼）**：同一張測試圖的縮圖與原圖——沒登入拿不到；偽造的 cookie 拿不到；登入後拿得到，回應標明不可快取、檔案裡沒有附加資料；**登入的人讀過之後，沒登入的人用同一個網址（以及加參數、帶 Range、HEAD）還是拿不到**；登出後舊的 cookie 拿不到；站主撤銷所有登入後拿不到；換密碼後拿不到、舊密碼不能再登入。
  其中「撤銷」與「換密碼」要到管理頁按按鈕，腳本會停下來等你（加 `--no-prompt` 就不等，這兩項記為無法判定）。
- **`--reply`**：登入後送出一則標明是測試的回覆，同一則再送兩次（同一次登入重送、重新登入之後重送），再請你到管理頁的收件匣確認收到、而且**只有一則**（確認後請刪掉）。腳本自己看不到資料庫，「只有一則」要由人確認。
- **`--rate`**：連續送幾次錯的密碼，確認會被限速（會讓你當下的 IP 最多 10 分鐘不能登入；管理頁可以解除）。要先看到「密碼不對」、之後才開始被擋才算通過；如果第一次就被擋（這個 IP 已經在限速中），結果是無法判定，請先到管理頁清除限速紀錄再跑。
- **`--preview-url <網址>`、`--r2-url <網址>`**：有版本的預覽網址（`https://<版本編號前 8 碼>-<Worker 名稱>.<子網域>.workers.dev`，版本編號用 `npx wrangler versions list -c visitor/wrangler.jsonc` 查）或儲存桶曾經有過的公開網址時，可以實際打開看看。**這兩項只抓得到「開著」**：連得到這個專案的 Worker、被轉到 Access、拿得到圖片 → 沒通過；其他回應（找不到、被拒絕、被限速、伺服器錯誤、轉到別處）一律是無法判定，不會回報通過——網址打錯或版本編號不存在時，回應也是找不到。是不是真的關閉，以後台與 `wrangler` 看到的設定為準（ACCEPTANCE.md 的 B-2）。
- `--report <檔名>` 會把結果另外寫成 JSON（不含密碼與 cookie），可以附在驗收紀錄裡。**這個檔案不要 commit**（裡面有你的網址）；上面的寫法把它放在家目錄，不在 repo 裡。

**訪客密碼**只從環境變數 `ROOM_TEST_PASSWORD` 讀取，或在執行時輸入（不顯示）；不接受命令列參數，不會被印出來，也不會寫進報告。請只用「範例內容階段」的測試密碼來跑：檢查的過程會請你換掉它。

腳本檢查不到、**仍然要由人確認**的項目，每次執行完都會列在最後（管理端的 MFA、Access 的政策、R2 的公開入口、預覽網址、各主要操作的 CPU 用量、真實的 iPhone Safari、泡泡在傳送之前可以確認的事）。這些連同腳本的結果，一起記在 [ACCEPTANCE.md](ACCEPTANCE.md)。

### CPU 用量怎麼量

免費方案每一次請求的 CPU 時間上限是 10 ms，超過時那一次請求會失敗（訪客看到的是平台的錯誤頁）。本機量不到正式環境的數字，所以要在正式環境量：

- **後台**：Workers & Pages → 該 Worker → Metrics。看 CPU Time，以及 Errors → Invocation Statuses 裡有沒有 `Exceeded CPU Time Limits`。
- **即時**：開著下面的指令，同時在瀏覽器裡把每一種操作各做幾次，再按 Ctrl+C：
  ```bash
  npx wrangler tail ayaka-room --format json | node scripts/cpu_report.mjs --expect visitor
  npx wrangler tail ayaka-room-admin --format json | node scripts/cpu_report.mjs --expect admin
  ```
  它會依「操作」（方法＋路徑）列出「有效量測數／總請求數」與 CPU 毫秒（最小／中位／最大），不印網址參數、標頭或記錄內容。結果有三種（結束代碼 0／1／2）：
  - `✖` 沒通過：有請求達到或超過上限，或被平台以「超過 CPU 上限」中止。
  - `？` 無法判定：沒有收到請求；**有任何一筆請求缺少有效的 CPU 數值**（`cpuTime` 欄位不存在，或不是有限、非負的數字——不會拿 `wallTime` 代替）；或加了 `--expect` 而有主要操作還沒量到。缺資料的那一列會標出來。這時請重新量一次，或以後台的 Metrics 為準。
  - `✔` 通過：收到的每一筆都有數值而且低於上限；加了 `--expect visitor`／`--expect admin` 時，還要那個 Worker 的每一種主要操作都至少量到一筆。

  「開專區頁面」請在已經登入的狀態下量（沒登入時同一個網址只是登入表單，腳本從紀錄裡分不出來）。這個腳本還沒有對正式環境的輸出驗證過；`cpuTime` 這個欄位如果不存在，結果會是無法判定，不會被當成通過。

要量的操作：登入、開專區頁面、縮圖、原圖、送出回覆、登出（訪客端）；開管理頁、上傳照片、產生密碼（管理端）。**最可能接近上限的是上傳照片**：要解析幾 MB 的表單、再把 JPEG 走過一遍。Cloudflare 的文件說一般的 Worker 平均約 2.2 ms，處理驗證或解析大量資料的通常是 10–20 ms。本機粗估，清理一張 3.7 MB 的 JPEG 大約 5 ms（不含解析表單；不同機器不能直接比）。如果正式環境量到上傳超過上限，可以先把上傳的尺寸或品質調低（`admin/client/admin.js` 的 2000 與 0.88），或改用付費方案。

## 日常操作

都在管理頁：

- **看回覆**：收件匣。可以單則刪除、全部匯出成 JSON。
- **換合言葉**：「密碼與登入」→ 產生一組新的密碼（8 組十六進位字，只顯示一次，請當下複製）。舊密碼立刻失效，已登入的人也會被登出。不小心重新整理那一頁、或連按兩下，都不會再換一次（換密碼的表單只會生效一次）。合言葉只能用產生的，不能自己取。
- **不換密碼、只讓所有人重新登入**：「撤銷所有訪客的登入」。
- **有人打錯太多次被擋住**：「清除登入的限速紀錄」。
- **換照片或文字**：「照片」、「標題與留言」。照片上傳需要 JavaScript（重新編碼在瀏覽器裡做）。

其他：

- **懷疑金鑰外流**：重新執行 [DEPLOY.md 的階段 4](DEPLOY.md#階段-4金鑰)設定新的 `PEPPER` 與 `SESSION_SECRET`。換了 `PEPPER` 之後原本的合言葉會失效，要到管理頁重新產生。
- **刪除的資料**：管理頁的刪除會把資料從資料庫與儲存桶移除。但 D1 有「Time Travel」還原功能，免費方案可以還原到 7 天內的任何時間點，所以刪掉的回覆在這段期間內，帳號擁有者仍然還原得回來。
- **整個關掉**：在 Cloudflare 後台刪除兩個 Worker、資料庫與儲存桶，並把 `data.js` 的 `site.roomUrl` 改回 `null`。

## 費用與額度

2026-11-15 依官方文件整理（出處在最後一節）。Cloudflare 的方案常常調整，開通前請再看一次官方頁面。

| 服務 | 免費方案的額度與限制 | 開通時要不要付款資料 |
| --- | --- | --- |
| Workers（Free） | 每天 100,000 個請求（UTC 午夜重置；超過時回 Error 1027）。每一次請求 CPU 時間 10 ms（超過時回 Error 1102）。每一次請求最多 50 個子請求 | 不用 |
| D1（Free） | **每個資料庫最大 500 MB；整個帳號合計 5 GB**；最多 10 個資料庫。每天讀 500 萬列、寫 10 萬列，到達之後當天無法再查詢。Time Travel（還原）7 天 | 不用 |
| R2 | 每月的免費用量：10 GB-month 的儲存、100 萬次 Class A 操作、1,000 萬次 Class B 操作（只適用 Standard 儲存）。超過的部分按月依用量計費 | **要走結帳流程**：建立第一個儲存桶之前，要先在後台加上 R2 訂閱。官方文件沒有明寫這一步要不要填付款方式，以結帳畫面為準 |
| Zero Trust（Cloudflare Access）Free | 上限 50 人；這裡只有站主 1 人。付費的 Pay-as-you-go 是每人每月 7 美元。independent MFA 屬於哪個方案，官方沒有寫（見「管理端的多因素驗證（MFA）」） | **要**：開通時要選方案並填付款資料；選 Free 方案不會收費 |

**免費夠不夠用，要看實際的 CPU 與用量，現在還不能下結論：**

- 用量：以「一位訪客、幾十張照片」的規模，請求數、資料庫與儲存空間離上表的額度都很遠（開一次專區大約 5–15 個請求、每個請求讀寫幾列；每張照片的原圖加縮圖通常不到 1 MB，上限約 4.6 MB）。
- CPU：每一次請求 10 ms 的上限**還沒有在正式環境量過**。最可能超過的是管理端上傳照片（見「CPU 用量怎麼量」）。量到超過的話，要調整程式或改用 Workers 付費方案（每月最低 5 美元）。
- 程式大小：免費方案的上限是壓縮後 3 MB。兩個 Worker 用 `wrangler deploy --dry-run` 打包的結果是訪客端 51.63 KiB（gzip 14.80 KiB）、管理端 117.00 KiB（gzip 32.28 KiB）。
- 超過 Workers 的每日請求數或 D1 的每日讀寫量時，服務會停止回應到額度重置，不會自動收費。R2 超過免費用量的部分會收費。
- D1 免費方案另外限制每一次請求最多 50 句查詢；這裡每個請求用到的查詢最多十幾句。
- 有人惡意大量送請求可以把每天 100,000 個請求的額度用完，讓專區當天打不開（內容不會外洩）。應用程式自己的限速擋不了這件事；要在請求到達 Worker 之前就擋，得接自己的網域來設定 WAF 規則（目前沒有，見「四層防護」）。
- 不想填付款資料的話，這個架構就不能用 R2 與 Access：照片可以改存在 D1（要改程式，而且受單一資料庫 500 MB 的限制）；但管理端的登入與第二因子就得自己做，需要另一輪設計與審查。

## 已知限制

- **合言葉是共用的**：拿到的人都能看、都能回覆，網站分不出誰是誰。管理頁上回覆的「登入代號」只能看出「是不是同一次登入送的」。合言葉寫在訊息裡，看得到那則訊息的人就能登入。
- **合言葉很長**（32 個十六進位字）：用複製貼上沒有問題，手打很辛苦。泡泡裡能不能複製訊息的文字，傳送之前只在既有的訊息上確認（ACCEPTANCE.md 的 C-2），不為了這件事送出訊息；不能複製的話需要另外想辦法，請不要為了好打而回頭用短的或自己取的密碼。
- **對方那邊的泡泡畫面驗證不到**：站主看得到的只有粉絲端（自己的 App）。藝人收件端裡網址能不能點、文字能不能複製、訊息會不會被看到，從粉絲端看不出來；沒有直接證據之前，這些在驗收紀錄裡都是「未驗證」（ACCEPTANCE.md 的 E 區），不會用粉絲端或電腦上的結果代替；它們也不是正式內容定稿的前置條件。
- **不是端對端加密**：資料在 Cloudflare 上，能登入站主 Cloudflare 帳號的人（以及 Cloudflare 這個平台）技術上讀得到。請保護好 Cloudflare 帳號。
- **限速用的是固定時間窗**，而且以 IP 計：同一個網路下的人共用額度；換 IP 可以重新計數（所以另外有「所有來源合計每小時 200 次」的上限）。反過來，有人可以故意把這個合計上限用完，讓其他人暫時無法登入；站主可以在管理頁清除。
- **管理端的第二因子靠的是 Access 的設定**：管理端的程式看不出「這次登入有沒有完成第二因子」（見「管理端的多因素驗證（MFA）」），所以那一節的驗收不能省。
- **本機測試不等於正式環境**：Access 的實際登入與第二因子、邊緣的行為、CPU 時間、真實的手機，都要部署後確認（ACCEPTANCE.md）。瀏覽器測試用的是 Chromium 的手機尺寸，不是 iPhone 的 Safari。
- **照片清理看的是檔案的結構，不解碼影像**：藏在壓縮資料或畫面本身裡的東西，伺服器看不到；那一層靠上傳前由瀏覽器整張重新編碼。不經過管理頁、直接把原檔送到伺服器的話：Exif 裡的拍攝方向也會被去掉（照片會回到儲存時的方向），色彩描述檔（ICC）也會去掉（廣色域的照片顏色會偏淡）。請一律從管理頁上傳。
- **切換語言、重新整理或關掉分頁時，寫到一半的回覆不會留下來**（草稿只存在那一頁的輸入欄裡，不寫進瀏覽器的儲存空間）。登入過期時不會丟，因為那時不用離開頁面。
- **回覆的去重認的是送出編號，重新整理之後就是新的編號**：回覆其實已經存好、只是成功的回應沒有送到時，留在同一頁重送（包含中間重新登入）只會有一筆；但如果重新整理或重新打開頁面，再打一次同樣的內容，會存成第二則。伺服器不會只因為文字相同就當成重複（那樣的話，想送兩則一樣的話也送不出去）。同一個送出編號配上改過的內容，會當成新的一則存下來（兩個版本都留著）。
- **`check_deployed.mjs` 的 `--preview-url`、`--r2-url` 證明不了「已經關閉」**，只抓得到「開著」。預覽網址與儲存桶公開入口是不是關閉，要看後台或 `wrangler` 的設定。
- **直接在分頁裡打開一張照片**（例如沒有 JavaScript 時）會看到瀏覽器內建的看圖頁；因為 CSP 不允許 inline 樣式，它的置中與縮放樣式不會套用，照片本身正常顯示。
- 管理頁的上傳表單需要 JavaScript；訪客端沒有 JavaScript 也能用。
- 還沒做的：回覆通知（有新回覆時寄信）、照片批次上傳、多位管理者的權限區分。

```
backend/
├─ README.md                 這份說明

│   └─ public/               任何人都拿得到的靜態檔：room.css、room.js、favicon.svg（沒有私人內容）；_headers 是這些檔案的回應標頭

│   ├─ wrangler.jsonc        部署設定

│   └─ client/admin.js       管理頁在瀏覽器裡執行的腳本（刪除前確認、照片重新編碼）
```
